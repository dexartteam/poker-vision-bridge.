# Пошаговые промпты для разработки распознавания покерного стола

## Какой результат ожидаем после завершения работы

Получаем работающее веб-приложение первого этапа AI Poker. Пользователь подключает вебкамеру, выделяет область стола и своё место, запускает наблюдение. Сайт показывает видео и распознанные карты, места игроков, стеки, ставки, банк и индикатор хода. Изображения отправляются в OpenAI API по существенным изменениям и для ограниченной перепроверки. Сервер выдаёт версионируемый поток полных состояний JSON.

У результата видны возраст, источник и неопределённость. Система отличает нечитаемое значение от нуля, старое наблюдение от свежего и текущую картину от полной истории действий. Ошибка API, движение камеры или запоздалый ответ не превращаются в подтверждённое новое состояние.

Человек, открывший репозиторий, может найти модуль камеры, детектор изменений, очередь, адаптер OpenAI, правила сборки состояния и транспорт. У каждого модуля есть небольшой публичный интерфейс и тесты. Проект устанавливается по lockfile, проверяется одной командой и запускается по README.

На этом этапе реализуется распознавание и передача состояний. Ранее выбранные PokerAI, Telegram и стенд Open Poker для ботов остаются следующими интеграциями. Их адаптеры пока не пишем; контракт потребителя не выдумываем. `decision_ready` в первом этапе всегда `false`, с причиной `consumer_profile_not_configured`. Это не мешает получить полностью работающий диагностический сайт.

Исходный профиль: камера снимает один покерный стол на мониторе, шесть мест, Texas Hold’em. Шесть мест сохраняют прежнюю договорённость; вариант игры и особенности интерфейса проверяются на предоставленной записи. Для физического стола потребуется отдельный профиль.

Документ подготовлен 11 сентября 2026 года. Это инструкции для будущей реализации и проверки кода. Приведённые команды должны быть созданы соответствующими шагами; их результаты в этом документе не заявляются как уже полученные.

## Как пользоваться документом

1. Передать этот файл Codex в рабочем репозитории проекта. Сохранить копию под `docs/codex-implementation-guide.md`.
2. Выполнять промпты по порядку, начиная с 01. Каждый текстовый блок можно копировать как отдельное задание. Codex должен прочитать также расположенные сразу после него тесты.
3. Переходить к следующему шагу после прохождения его автоматических проверок. При ошибке Codex исправляет текущий шаг и повторяет затронутые проверки.
4. Если отсутствует камера, API-ключ или реальная запись, продолжать доступную разработку и автоматические проверки на подготовленных данных. Аппаратную или live-проверку отметить как невыполненную с конкретной причиной. Она остаётся условием соответствующей итоговой приёмки.
5. После каждого шага Codex обновляет `docs/PROGRESS.md`: результат, изменённые модули, точные команды, коды завершения, выполненные и невыполненные сценарии, следующий шаг.

Этот документ включает согласованные уточнения по отбору кадров и достаточен без предыдущей переписки. В экономном режиме страховочная перепроверка выполняется каждые 15 секунд; прежние 2 секунды остаются диагностической настройкой. Такая перепроверка не продлевает автоматически срок актуальности распознанных данных.

## Подход к модульности

Для нового проекта предлагаем TypeScript, React в браузере, Node.js на сервере, Zod для runtime-схем, Vitest и Playwright для проверок. Один репозиторий и один серверный процесс. Для существующего репозитория сначала изучить принятую структуру и сохранить рабочие решения; соответствие модулей документировать. Версии инструментов и SDK проверить при реализации, закрепить в lockfile и `packageManager`.

| Путь для нового проекта | За что отвечает | Что может импортировать |
| --- | --- | --- |
| `packages/contracts` | Схемы JSON, типы, версии, общие коды ошибок | Библиотеку схем; собственные файлы |
| `apps/web/src/capture` | Камера, жизненный цикл видео, подготовка пикселей | Контракты, браузерные API |
| `apps/web/src/calibration` | Геометрия стола, области, маски, опорные элементы | Контракты, функции геометрии |
| `apps/web/src/change-detection` | Чистое сравнение областей и оценка стабильности | Контракты, чистые функции обработки пикселей |
| `apps/web/src/transport` | Загрузка кадров, статусы захвата, получение SSE | Контракты, HTTP-клиент |
| `apps/web/src/ui` | Камера, распознанный стол, состояния интерфейса | Публичные интерфейсы клиентских модулей |
| `apps/api/src/application` | Связывает события, очередь, reducer и адаптеры | Публичные интерфейсы серверных модулей |
| `apps/api/src/scheduler` | Единственная очередь распознавания и лимиты | Контракты, интерфейсы часов и распознавателя |
| `apps/api/src/recognition` | Интерфейс распознавателя, адаптеры OpenAI и fixtures | Контракты; SDK только внутри адаптера OpenAI |
| `apps/api/src/table-state` | Чистый reducer, нормализация, раздачи, свежесть | Контракты, чистые функции и переданное время |
| `apps/api/src/http` | Авторизованные HTTP-маршруты и SSE | Контракты, интерфейс application |
| `apps/api/src/storage` | Запись сессий, миграции, экспорт | Контракты, драйвер хранения |
| `tests/fixtures` | Синтетические кадры, ожидаемые наблюдения, сценарии | Только тестовый код; реальные записи отдельно |

Внутри модуля зависимости могут быть подробными, наружу экспортируется только необходимое. Между модулями использовать публичный `index.ts`, без импорта внутренних файлов соседнего модуля. На границах проверять входные данные runtime-схемами. Не создавать пакеты для каждой функции, универсальный DI-фреймворк, брокер сообщений или микросервисы для этого MVP.

Доменный reducer не обращается к React, DOM, HTTP, базе, OpenAI, системному времени и случайным ID. Пример интерфейса: `reduceTableState(previous, event, policy) -> { next, effects }`; время и идентификаторы входят в событие. Исполнение эффектов принадлежит application.

Детектор получает пиксели, маски, эталоны и конфигурацию; возвращает `ChangeReport`. Таймеры, обращения к сети и публикацию событий выполняет клиентский контроллер. Модуль распознавания предоставляет `Recognizer.recognize(input, abortSignal) -> RecognitionOutcome`; scheduler не знает формат ответа SDK.

Время, ID и внешние эффекты внедряются через небольшие интерфейсы `Clock`, `IdGenerator`, `Recognizer`, `SessionRepository`. Различать монотонное время для интервалов и UTC для отображения. Достаточно обычных параметров конструктора или фабрики.

В `AGENTS.md` закрепить карту модулей, правила импортов, тестовые команды и инварианты. Для значимых решений вести короткие ADR в `docs/adr`: проблема, выбранное решение, последствия, дата. В каждом существенном модуле нужен короткий README с ответственностью, публичным API и примером. Не переносить туда пересказ всего кода.

## Инварианты проекта

1. Модель возвращает наблюдение изображения. Сервер определяет нормализованное состояние, свежесть и пригодность данных.
2. `null` означает неизвестное значение; `0` — установленный ноль. Пустое место, закрытые карты, сброс и нечитаемый экран различаются.
3. Все шесть мест имеют постоянные `seat_id`. Ники, дилер и позиции не меняют нумерацию.
4. Два слота своих карт и пять слотов борда сохраняют позиции даже при неизвестных значениях. У карты ранг и масть могут быть частично прочитаны.
5. Суммы нормализуются в целые минимальные единицы с `unit` и `scale`. Запретить отрицательные суммы, небезопасные для JSON number целые и неоднозначный разбор. Семантика ставки и включение её в банк определяются профилем.
6. Сравнение с предыдущим кадром оценивает движение; с последним принятым эталоном — необходимость распознавания; с отправленным кадром — повторную отправку. Отдельный `change_anchor` хранит вид, для которого уже зарегистрировано существенное изменение. Он нужен для определения следующего перехода и не заменяет принятый эталон. Неудачный или не принятый результат не сдвигает принятый эталон.
7. `frame_seq` растёт с захватом кадров. Отдельная `visual_revision` растёт только при новом существенном переходе относительно `change_anchor`. Последовательность A → B → B → B создаёт одну новую ревизию; переход B → C создаёт следующую. Сохранение отличия B от ещё не обновлённого принятого эталона A не создаёт ревизию повторно.
8. `session_id`, `capture_epoch`, `calibration_id`, `visual_revision`, `frame_id`, `frame_seq` и время берёт приложение. Модель не может подменить привязку ответа.
9. Обнаруженное существенное изменение сразу снимает подтверждение затронутой группы данных. Поздний ответ по прежней ревизии не возвращает актуальность.
10. Ставки, банк, текущий игрок и кнопки образуют согласованную динамическую группу. Запрещено молча склеить их из разных моментов и объявить результат подтверждённым.
11. Один scheduler владеет очередью. На стол — один активный запрос и один заменяемый ожидающий кадр; начальный общий лимит провайдера также один. Браузер не создаёт вторую независимую очередь распознавания.
12. Перезапуск камеры, смена режима или калибровки обесценивают несовместимые задания. Проверять эпоху и калибровку перед применением результата и перед продвижением эталона.
13. Возраст считается от захвата; heartbeat и повторная публикация его не обнуляют. Истечение срока применяется по таймеру даже при неподвижном столе.
14. Начало новой раздачи требует достаточных признаков. Одна анимация исчезновения карт не сбрасывает раздачу. Сомнение в границе не позволяет переносить старые карты в предполагаемую новую раздачу.
15. Редкие снимки не доказывают полноту истории. Статус истории по умолчанию `unknown`; доказанный пропуск или запуск посреди раздачи — `incomplete`. Разница `frame_seq` сама по себе не доказывает пропуск игрового действия.
16. Число, названное моделью `confidence`, не является измеренной вероятностью правильности. Согласие двух ответов тоже не устраняет систематическую ошибку чтения.
17. `mock`, `replay` и `live` явно различаются в UI, API, журнале и отчётах. Ошибка live не переключает приложение на mock.
18. Ключи находятся на сервере. Доступ к сессии проверяется для загрузки, статусов, чтения состояния, SSE, экспорта и удаления.

Причина отправки входит в контракт: `initial`, `significant_change`, `confirmation`, `safety_poll`, `retry`, `manual`, `hero_turn`. Новый захваченный кадр с теми же пикселями допустим для подтверждения, периодической проверки, ограниченного повтора, ручной проверки и свежей проверки нашего хода. Для каждого повода проверяется его условие: срок poll истёк, confirmation действительно запрошен, retry разрешён и так далее. Повтор одного `frame_id` всегда идемпотентен. Ни один повод не обходит очередь, лимит или бюджет. Переход нашего хода регистрируется как событие, а не повторяется на каждом кадре видимых кнопок.

## Начальная конфигурация

Это стартовые значения для пилота, а не измеренные характеристики системы. Все параметры находятся в типизированном конфиге, проверяются при запуске и сохраняются вместе с записью.

| Параметр | Значение |
| --- | --- |
| Запрашиваемое видео | 1920×1080, 30 кадров в секунду, с проверкой реально доступного режима |
| Локальное сравнение | 5 раз в секунду |
| Спокойный интервал значимых областей | 400 мс |
| Максимальное ожидание спокойствия | 1000 мс; по истечении кадр не становится достоверным автоматически |
| Страховочная перепроверка | 15 секунд в экономном режиме, 2 секунды в диагностическом |
| Предел возраста динамической группы | 5000 мс для пилота |
| Минимальный интервал запросов | 1000 мс с учётом повторов |
| Лимит запросов | 60 запусков за скользящие 60 секунд, все поводы и повторы вместе |
| Очередь | Один активный и один последний ожидающий кадр |
| Таймаут распознавания | Настраиваемый; стартовый транспортный предел 15 секунд |

Таймаут API 15 секунд не означает, что ответ с возрастом 14 секунд пригоден для текущего состояния: его можно сохранить как диагностику, но не объявить свежим при TTL 5 секунд. Если в экономном режиме стол не меняется 15 секунд, состояние после 5 секунд становится `stale` и ждёт перепроверки. Это ожидаемое поведение. Появление нашего хода создаёт приоритетный запрос свежего кадра в рамках лимитов.

## Как устроены проверки

Первый промпт создаёт команду `pnpm verify:step NN`. Она проверяет существование группы этапа, запускает lint, typecheck, проверку архитектурных импортов и `test:step:NN`, возвращая ненулевой код при любой ошибке. Соответствующий промпт обязан создать свой скрипт `test:step:NN` до проверки. Команда не должна объявлять успешными ещё не реализованные этапы.

Автоматические тесты используют Vitest для функций и серверных модулей, Playwright для интерфейса. Часы, сеть и видеовход контролируются. Для таймеров использовать fake timers вместо реального ожидания: [Vitest — Timers](https://vitest.dev/guide/mocking/timers). Подмены браузерных API устанавливать до запуска кода страницы: [Playwright — Mock browser APIs](https://playwright.dev/docs/mock-browser-apis).

Каждый пункт с ID в таблице ниже становится именованным тестом или однозначно проверяемым сценарием. Запрещены `--passWithNoTests`, пропущенные обязательные тесты, `todo` вместо проверки, успешный exit при отсутствии подходящих файлов и проверки только существования функций. Не подменять сам проверяемый detector, scheduler или reducer. Подменять следует их внешние зависимости.

После изменения прежнего модуля запускать его затронутые регрессии. Полный набор `pnpm verify` запускается перед итоговой передачей. Live API не входит в обычный CI и deterministic gate. У всех live-команд есть явные ограничения числа запросов и расходов; до их запуска используются настроенные серверные секреты и доступные механизмы получения ключа, без вывода ключа в чат или журнал.

```text
unknown и ошибочно уверенные значения. Для pipeline считай запросы/мин,

долю времени confirmed/fresh/partial/stale и ошибки границ раздачи.
Расчёт не должен поощрять превращение всех сложных полей в null.

Создай pnpm evaluate с явно разными режимами recorded и live. Recorded
использует записанные ответы и не проверяет текущую модель. Live требует
ключ, тарифы, max-requests и max-usd; каждый повтор учитывается. При отсутствии
обязательных данных или метрик отчёт не может получить статус passed.
Пороги реальной приёмки устанавливаются по пилоту на tuning и фиксируются
до control; статус без численных порогов — uncalibrated, а не success.

Сохрани машинный JSON и читаемый Markdown-отчёт. Добавь test:step:11 для
проверки расчётов и маршрутов оценки независимо от наличия реальной камеры.
```

## Правила дальнейшего развития

### Когда меняется формат данных

Сначала определить совместимость. Затем изменить runtime-схему и вывести типы, обновить fixtures, сериализацию, reducer, UI и внешних потребителей, добавить миграцию или явный отказ для старой версии. Проверить чтение старых записей. Новое значение enum тоже может нарушить потребителя; его нельзя считать безопасным автоматически. Изменения схемы и объяснение миграции идут вместе.

### Когда меняется алгоритм

Изменение detector, порогов, промпта или модели оформляется новой версией эксперимента. Сначала тесты затронутого модуля и replay регрессий, затем оценка на фиксированном наборе. Сравнивать качество, покрытие, задержку и число запросов одновременно. Уменьшение числа запросов ценой пропуска важных изменений должно быть видно в отчёте.

### Когда добавляется следующий сервис

Будущий адаптер решений подписывается на тот же `TableSnapshot` через документированный порт/транспорт. Перед его добавлением изучить реальный контракт сервиса и определить `consumer_profile`: обязательные поля, свежесть, требования к истории, идентификация раздачи и допустимые действия. Только тогда реализовать серверное вычисление `decision_ready`. Адаптер не меняет логику камеры, детектора и распознавателя напрямую.

### Что должен понимать новый разработчик

Он должен суметь проследить один frame_id от захвата до snapshot и объяснить: почему кадр отправили, какое наблюдение вернула модель, какие проверки прошли, почему данные стали confirmed или partial, к какой раздаче относятся и насколько устарели. Если для этого нужно читать весь репозиторий, границы или документацию следует улучшить.

## Официальные материалы для реализации

Responses API поддерживает изображения и передачу нескольких изображений в запросе; crops следует связывать с одним исходным кадром по контракту нашего приложения. Мелкий текст требует отдельной проверки читаемости: [OpenAI Images and vision](https://developers.openai.com/api/docs/guides/images-vision).

Structured Outputs задаёт форму ответа через JSON Schema; соответствие форме не гарантирует правильность распознанных значений. Нужно отдельно обрабатывать refusal и incomplete: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Подключение камеры, разрешения и secure context описаны в [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia). Для обработки поступающих видеокадров используется поддерживаемый браузером механизм, например [MDN requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback); фактическую совместимость проверить в целевом браузере.

Для временных тестов — [Vitest Timers](https://vitest.dev/guide/mocking/timers); для ранней подмены браузерных API в E2E — [Playwright Mock browser APIs](https://playwright.dev/docs/mock-browser-apis). При реализации сверять установленную версию инструмента с его документацией, а не копировать устаревший синтаксис.

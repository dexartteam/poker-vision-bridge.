# Архитектура первого этапа

## Решение

Сохраняем существующий FastAPI-мост. Новый сервис запускается отдельным приложением
`app.vision.api:app`, чтобы даже случайная настройка старых интеграций не включала
решения или исполнение при тестировании камеры. Браузер: TypeScript, стандартные
DOM/Canvas API, Vite и отдельный Worker. React здесь не нужен для небольшого
интерфейса, а прежний Python-сервис не переписывается на Node.

Это адаптация исходного плана к обнаруженному репозиторию. Python-тесты остаются
на pytest; браузерная логика проверяется Vitest. Пакеты фиксируются lock-файлами.

## Модули и направления зависимостей

| Модуль | Ответственность и публичный интерфейс |
| --- | --- |
| `web/core/profile.ts` | Типы областей, исходная раскладка, `validateProfile` |
| `web/core/detector.ts` | Чистый `Detector.step/accept/release`, сравнение RGB |
| `web/capture/camera.ts` | `Camera.start/stop`, разрешение и освобождение треков |
| `web/capture/freshness.ts` | `VideoFreshness.take/close`, только декодированные новые кадры |
| `web/detection/worker.ts` | Обмен сообщениями с чистым детектором |
| `web/transport/api.ts` | HTTP и доступ к собственной серверной сессии |
| `web/session/controller.ts` | Захват, источник, Worker, события изменений, доставка и остановка |
| `web/main.ts`, `web/ui/` | Отображение и пользовательские действия; никаких решений игры |
| `app/vision/contracts.py` | Версионированная граница: Profile, Source, Frame, Observation |
| `app/vision/provider.py` | OpenAI Responses API / явно выбранный mock |
| `app/vision/scheduler.py` | Владение сессиями, единственная очередь, лимиты и журнал |
| `app/vision/reducer.py` | Чистая обработка наблюдений, инвалидация и TTL |
| `app/vision/api.py` | Проверка доступа и изображений, HTTP-маршруты, статические файлы |
| `app/vision/replay.py` | Повтор reducer по записи, без провайдера |

Core не импортирует DOM, HTTP или UI. Provider не меняет состояние. Reducer не
использует сеть, часы ОС или генерацию идентификаторов: время передаётся явно.
Scheduler не импортирует старый мост. Скрипт `check:architecture` проверяет эти
границы. Для существенного расширения модуля сначала обновить этот документ.

## Как определяется изменение

Детектор работает с копией кадра шириной до 640 пикселей, пять раз в секунду.
Для каждой значимой области сравнивает RGB-каналы. Стартовый порог отличия пикселя
24/255; значимость — от 1,5% области или локальный блок 8×8 с достаточным изменением
не менее четырёх пикселей и 15% блока. Локальные блоки нужны, чтобы изменение одной
цифры не терялось на фоне большой области. Это настраиваемые гипотезы пилота,
не установленные на вашей камере пороги.

Четыре отдельных эталона:

1. Previous — движение между соседними проверками.
2. Change anchor — последняя зарегистрированная визуальная перемена. A→B→B
   увеличивает revision один раз, A→B→A — дважды.
3. Accepted baseline — кадр, чьё состояние сервер подтвердил по двум наблюдениям.
4. In-flight — уже предложенный кадр; повтор такой же картинки подавляется.

Память эталонов копируется: повторное использование буфера не меняет прошлые
кадры. Только `baseline_accepted=true` для текущей ревизии двигает baseline.
Ответ HTTP 202 означает постановку в очередь. Он никогда не подтверждает состояние.

Движение завершилось после 400 мс покоя. Через 1000 мс непрерывного движения
отправляется ограниченный диагностический кандидат `stable=false`. Он не может
подтвердить состояние; после успокоения отправляется новый стабильный кадр.
Изменение немедленно очищает актуальное состояние. Его сообщение идёт отдельно
от изображения и не ждёт окончания загрузки JPEG.

`frame_seq` считает новые захваченные кадры, `visual_revision` — значимые изменения.
Для видео новая проверка допускается только после `requestVideoFrameCallback`.
Один и тот же остановившийся видеобуфер не получает новую достоверную свежесть.

## Очередь и состояние

Одна активная операция провайдера во всём процессе, одна последняя ожидающая
картинка на каждую сессию. Новая ожидающая заменяет старую. Все причины, включая
ручные снимки, confirmation и retry, входят в лимит 60 попыток за скользящую минуту
и интервал 1000 мс. Ошибки провайдера включают общий backoff до 30 секунд.
Транспортный timeout не доказывает остановку вычисления на стороне OpenAI;
локальный слот освобождается, когда вызов адаптера завершился.

Ответ связан с epoch, calibration, revision и порядковым номером кадра. Старый
ответ сохраняется для диагностики, но не меняет текущее состояние. Новый источник
всегда получает новую сессию/epoch. Часы лимитов монотонные; время UTC для сервера
строится от стартовой UTC-точки и монотонного интервала. Захваты из будущего более
чем на 2 секунды или старше 5 секунд отклоняются.

Два разных стабильных кадра с совпадающими наблюдаемыми значениями и читаемой
обязательной группой дают `confirmed`. Совпадение null не подтверждает данные.
Дилер, банк, видимость карт, признак хода героя, известные места и суммы занятых
мест обязательны для такого подтверждения. Неизвестная история, семантика банка
или побочных банков не достраиваются: `decision_ready` всегда false. `confirmed`
означает устойчивое наблюдение выбранной группы, а не готовность к игре.

Наблюдение заменяется целиком; динамические значения разных моментов не склеиваются.
Карты предыдущей раздачи не переносятся в новую неизвестную картинку. Полной истории
действий и достоверного восстановления границы раздачи по редким кадрам эта версия
не обещает. `action_history.status` всегда `unknown`.

Через 5000 мс состояние становится stale. При экономном safety poll 15 секунд
это нормальный промежуток. Сама устарелость не запускает confirmation. Для свежего
первого кандидата confirmation разрешает новый захват с идентичными пикселями.

## Контракты и последующее развитие

`schema_version=1.0`. Модель возвращает Observation; Source задаёт приложение.
Суммы — целые минимальные единицы плюс raw-строка, unit и scale из профиля. JSON
schema отвергает дополнительные поля, дубликаты карт и мест, несогласованную улицу.
Не добавлять управляющие команды в Observation.

Следующая интеграция должна иметь отдельный consumer profile, проверку полноты,
свежести и hand identity. Она не должна получать `candidate`, `uncertain` или
`stale` как готовую команду. Только после согласования её контракта можно обсуждать
изменение `decision_ready`; текущая ветка не меняет существующий executor.

Известные границы MVP: без коррекции перспективы и дрожания камеры, без
специализированного OCR, без персистентной очереди, без восстановления полной
истории ставок, без поля-by-поля объединения наблюдений. Перспективу и положение
камеры сначала фиксируем физически и проверяем на реальном видео.

Адаптер построен по официальным руководствам:
[изображения](https://developers.openai.com/api/docs/guides/images-vision),
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

# Архитектура первого этапа

## Решение

### Локальное распознавание в браузере

Основной вход сайта теперь использует `web/local/`: захват → детектор изменений →
локальная очередь → OCR / шаблоны карт → частичный JSON. Изображения не отправляются
на сервер. Старый серверный интерфейс доступен отдельно в `/server.html`.
Статические Worker, WASM и языковая модель собираются из закреплённых npm-пакетов;
CDN и секреты для распознавания не требуются.

Для GitHub Pages режим сборки `pages` оставляет один HTML-вход и пишет только
статические файлы в `dist/pages`. Vite base равен `./`; OCR-пути разрешаются от
base и URL документа, поэтому подпапка репозитория сохраняется. Обычная сборка
оставляет прежние два входа и корневые пути для FastAPI. Сборка Pages не содержит
ссылки на серверный режим и не включает приватный набор изображений/шаблонов.
Workflow проверяет статический артефакт в PR, а публикует только из `main`.
Окружение `github-pages` сохраняет ограничение на эту ветку; PR не запускает deploy.

`web/local/contracts.ts` хранит собственный контракт `local-vision.observation.v1`
и калибровку. `fields.ts` разбирает OCR, `cards.ts` обрабатывает пиксели и шаблоны,
`recognizer.ts` управляет переиспользуемым Tesseract Worker. Чистый `gate.ts` владеет
очередью и проверками версии/времени; `controller.ts` связывает его с видеовходом
и Worker детектора. `main.ts` отвечает только за интерфейс и калибровку.

Одна операция распознавания и один последний ожидающий кадр. Изменение сразу
инвалидирует текущее состояние. Ответ старше 5 секунд либо от прежней версии кадра
не применяется через `applied`. После проверки сессии, калибровки и порядка кадров
он может попасть только в отдельный `outdated` callback с `status=stale`: интерфейс
показывает последнее чтение с временем исходного кадра, журнал сохраняет этот статус.
Историческое чтение не участвует в подтверждении. Ответы закрытой или чужой сессии
полностью отбрасываются. Полный кадр и профиль копируются. Перемотка, пауза,
конец видео и остановка закрывают сессию; повтор одного видеобуфера не создаёт
нового наблюдения. Два свежих стабильных кадра могут подтвердить повторяемость
прочитанных полей, но общее состояние остаётся `partial`, `decision_ready=false`.

Источник `recording` не превращается в камеру от надписи LIVE внутри видео.
В профиле Open Poker REPLAY/неизвестный режим не выдаёт текущий банк или карты. OCR и карточные
наблюдения одного кадра не смешиваются с прошлыми. Закрытые карты, места,
статусы игроков и история действий не домысливаются.

Первый профиль настроен по записи Open Poker 1206×2622. Число пикселей не доказывает
правильность калибровки: перед запуском пользователь проверяет области. Шаблоны загружаются пользователем из локального JSON
`local-vision.cards.v1` и копируются в сессию. Без них карты остаются неизвестными;
текстовый OCR продолжает работать. Набор шаблонов ограничен реально видимыми девятью картами; результаты остаются частичными.
Шаблоны из одной раздачи и проверка записанного экрана не доказывают качество на
всей колоде или вебкамере. Переход к общему контракту Observation и игровому consumer
потребует отдельной реализации и проверки полноты; этот этап их не включает.

### Профиль PokerStars classic

Выбор интерфейса явный. Старый Open Poker сохраняет profile/observation v1;
PokerStars использует `local-vision.profile.v2` с `layout=pokerstars-classic` и
`local-vision.observation.v2`. Импорт отвергает неизвестные версии, раскладки,
неполные области и несовместимые наборы шаблонов.

| Модуль `web/local/pokerstars/` | Ответственность |
| --- | --- |
| `profile.ts` | Геометрия шести мест, карт и надписей; координаты нормализованы |
| `preprocess.ts` | Чистое выделение областей, подготовка OCR, цвет надписей и активных кнопок |
| `symbols.ts`, `cards.ts` | Угловые символы ранга/масти, качество изображения и отказ при неоднозначности |
| `fields.ts` | Чистый разбор чисел и видимых подписей; отсутствие истории между кадрами |
| `recognize.ts` | Все области одного неизменяемого кадра; внедряемые OCR и карточный reader |

DOM, создание Tesseract и Worker остаются в общем `recognizer.ts`. Карты читаются
в `card.worker.ts`; контроллер, детектор, ограничение частоты и защита от старых
ответов общие. Профиль и шаблоны копируются при запуске сессии. Приватные данные
для тестов и шаблоны пользователь выбирает локально; в сборке они отсутствуют.

Шесть мест нумеруются 0–5 по часовой стрелке сверху, герой — место 3. JSON добавляет
`hero_cards`, `seats`, `hero_turn`, `available_actions` и неполную `action_history`.
`chip_display` — прочитанная сумма у места, `chip_visibility` — видимость текста.
Она может означать ставку или выплату, поэтому `bet=null`; пустота не становится 0.
Белая надпись All-In в области стека даёт статус, а не выдуманный нулевой стек.
Голубая подпись действия должна пройти цветовой gate и строгий OCR-парсер; белый
ник Fold не считается пасом. Список доступных действий появляется только при
подтверждённых красных кнопках Call/Raise либо Check/Bet. Тёмные кнопки и флажки
предварительного выбора не подтверждают ход; отсутствие кнопок даёт null.

Номер раздачи, дилер, принадлежность банка текущим ставкам неизвестны. Чат с итогом
прошлой раздачи не читается и не является самостоятельной областью детектора.
Этап выводится только из достоверно прочитанного непрерывного борда; любой
неопределённый слот оставляет этап неизвестным. Дубликаты карт между бордом и
героем отклоняются. Поля разных кадров не склеиваются. Этот профиль не получает
`repeated`: без достоверной идентичности раздачи он остаётся одиночным частичным
наблюдением с прежними TTL/инвалидацией и `decision_ready=false`.

Для следующего этапа нужен отдельный модуль временного согласования: границы
раздач, дилер, действия с суммами, различение ставки и выплаты, полнота истории.
Он должен потреблять версионированные наблюдения и иметь собственные тесты
переходов, а не добавлять память или игровые решения в OCR либо UI.

### Сохранённый серверный путь

Сохраняем существующий FastAPI-мост. Новый сервис запускается отдельным приложением
`app.vision.api:app`, чтобы даже случайная настройка старых интеграций не включала
решения или исполнение при тестировании камеры. Браузер: TypeScript, стандартные
DOM/Canvas API, Vite и отдельный Worker. React здесь не нужен для небольшого
интерфейса, а прежний Python-сервис не переписывается на Node.

Это адаптация исходного плана к обнаруженному репозиторию. Python-тесты остаются
на pytest; браузерная логика проверяется Vitest. Пакеты фиксируются lock-файлами.

## Модули и направления зависимостей

| Модуль | Ответственность и публичный интерфейс |
| --- | --- |
| `web/core/profile.ts` | Типы областей, исходная раскладка, `validateProfile` |
| `web/core/detector.ts` | Чистый `Detector.step/accept/release`, сравнение RGB |
| `web/capture/camera.ts` | `Camera.start/stop`, разрешение и освобождение треков |
| `web/capture/freshness.ts` | `VideoFreshness.take/close`, только декодированные новые кадры |
| `web/detection/worker.ts` | Обмен сообщениями с чистым детектором |
| `web/transport/api.ts` | HTTP и доступ к собственной серверной сессии |
| `web/session/controller.ts` | Захват, источник, Worker, события изменений, доставка и остановка |
| `web/main.ts`, `web/ui/` | Отображение и пользовательские действия; никаких решений игры |
| `app/vision/contracts.py` | Версионированная граница: Profile, Source, Frame, Observation |
| `app/vision/provider.py` | OpenAI Responses API / явно выбранный mock |
| `app/vision/scheduler.py` | Владение сессиями, единственная очередь, лимиты и журнал |
| `app/vision/reducer.py` | Чистая обработка наблюдений, инвалидация и TTL |
| `app/vision/api.py` | Проверка доступа и изображений, HTTP-маршруты, статические файлы |
| `app/vision/replay.py` | Повтор reducer по записи, без провайдера |

Локальные модули используют только `core/detector`, `capture/freshness`,
`capture/camera` и `detection/worker` из общей части. Они не импортируют HTTP
transport или серверный controller; это проверяет архитектурный скрипт.
`preprocess.ts`, `fields.ts`, `cards.ts` и `gate.ts` не зависят от DOM. Изменение
модели или шаблонов проверяется на реальных изображениях, а изменение очереди —
на поведенческих тестах с подменёнными часами. OCR Worker закрывается при остановке,
в том числе если его создание завершилось уже после отмены запуска.

Core не импортирует DOM, HTTP или UI. Provider не меняет состояние. Reducer не
использует сеть, часы ОС или генерацию идентификаторов: время передаётся явно.
Scheduler не импортирует старый мост. Скрипт `check:architecture` проверяет эти
границы. Для существенного расширения модуля сначала обновить этот документ.

## Как определяется изменение

Детектор работает с копией кадра шириной до 640 пикселей, пять раз в секунду.
Для каждой значимой области сравнивает RGB-каналы. Стартовый порог отличия пикселя
24/255; значимость — от 1,5% области или локальный блок 8×8 с достаточным изменением
не менее четырёх пикселей и 15% блока. Локальные блоки нужны, чтобы изменение одной
цифры не терялось на фоне большой области. Это настраиваемые гипотезы пилота,
не установленные на вашей камере пороги.

Четыре отдельных эталона:

1. Previous — движение между соседними проверками.
2. Change anchor — последняя зарегистрированная визуальная перемена. A→B→B
   увеличивает revision один раз, A→B→A — дважды.
3. Accepted baseline — кадр, чьё состояние сервер подтвердил по двум наблюдениям.
   Локальный режим не подтверждает полное состояние и не двигает этот эталон.
4. In-flight — уже предложенный кадр; повтор такой же картинки подавляется.

Память эталонов копируется: повторное использование буфера не меняет прошлые
кадры. Только `baseline_accepted=true` для текущей ревизии двигает baseline.
Ответ HTTP 202 означает постановку в очередь. Он никогда не подтверждает состояние.

Движение завершилось после 400 мс покоя. Через 1000 мс непрерывного движения
отправляется ограниченный диагностический кандидат `stable=false`. Он не может
подтвердить состояние; после успокоения отправляется новый стабильный кадр.
Изменение немедленно очищает актуальное состояние. Его сообщение идёт отдельно
от изображения и не ждёт окончания загрузки JPEG.

`frame_seq` считает новые захваченные кадры, `visual_revision` — значимые изменения.
Для видео новая проверка допускается только после `requestVideoFrameCallback`.
Один и тот же остановившийся видеобуфер не получает новую достоверную свежесть.

## Очередь и состояние серверного пути

Одна активная операция провайдера во всём процессе, одна последняя ожидающая
картинка на каждую сессию. Новая ожидающая заменяет старую. Все причины, включая
ручные снимки, confirmation и retry, входят в лимит 60 попыток за скользящую минуту
и интервал 1000 мс. Ошибки провайдера включают общий backoff до 30 секунд.
Транспортный timeout не доказывает остановку вычисления на стороне OpenAI;
локальный слот освобождается, когда вызов адаптера завершился.

Ответ связан с epoch, calibration, revision и порядковым номером кадра. Старый
ответ сохраняется для диагностики, но не меняет текущее состояние. Новый источник
всегда получает новую сессию/epoch. Часы лимитов монотонные; время UTC для сервера
строится от стартовой UTC-точки и монотонного интервала. Захваты из будущего более
чем на 2 секунды или старше 5 секунд отклоняются.

Два разных стабильных кадра с совпадающими наблюдаемыми значениями и читаемой
обязательной группой дают `confirmed`. Совпадение null не подтверждает данные.
Дилер, банк, видимость карт, признак хода героя, известные места и суммы занятых
мест обязательны для такого подтверждения. Неизвестная история, семантика банка
или побочных банков не достраиваются: `decision_ready` всегда false. `confirmed`
означает устойчивое наблюдение выбранной группы, а не готовность к игре.

Наблюдение заменяется целиком; динамические значения разных моментов не склеиваются.
Карты предыдущей раздачи не переносятся в новую неизвестную картинку. Полной истории
действий и достоверного восстановления границы раздачи по редким кадрам эта версия
не обещает. `action_history.status` всегда `unknown`.

Через 5000 мс состояние становится stale. При экономном safety poll 15 секунд
это нормальный промежуток. Сама устарелость не запускает confirmation. Для свежего
первого кандидата confirmation разрешает новый захват с идентичными пикселями.

## Контракты серверного пути и последующее развитие

`schema_version=1.0`. Модель возвращает Observation; Source задаёт приложение.
Суммы — целые минимальные единицы плюс raw-строка, unit и scale из профиля. JSON
schema отвергает дополнительные поля, дубликаты карт и мест, несогласованную улицу.
Не добавлять управляющие команды в Observation.

Следующая интеграция должна иметь отдельный consumer profile, проверку полноты,
свежести и hand identity. Она не должна получать `candidate`, `uncertain` или
`stale` как готовую команду. Только после согласования её контракта можно обсуждать
изменение `decision_ready`; текущая ветка не меняет существующий executor.

Известные границы MVP: без коррекции перспективы и дрожания камеры, без
полного распознавания колоды и мест, без персистентной очереди, без восстановления полной
истории ставок, без поля-by-поля объединения наблюдений. Перспективу и положение
камеры сначала фиксируем физически и проверяем на реальном видео.

Адаптер построен по официальным руководствам:
[изображения](https://developers.openai.com/api/docs/guides/images-vision),
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
